# Woohoo 封闭 Beta 稳定化与发布准备 PRD

> 文档归档：`closed-beta-stabilization/v1.0`。

版本：v1.0  
日期：2026-08-24  
状态：已实施，待预发布演练  
适用阶段：封闭 Beta 稳定化（建议 3-4 周）

## 1. 背景与当前基线

Woohoo 已具备从协作输入到流水线编排、审核、重试、人工介入、图片/视频生成，以及分镜持久化的核心链路。当前产品形态适合进入小范围封闭 Beta 验证，但尚不适合直接面向广泛外部用户发布。

本 PRD 的目标不是扩展新的创作能力，而是将既有链路变为可部署、可恢复、可验证、可运营的 Beta 产品。它是本阶段的执行基线；`docs/multi-agent-orchestrator-beta-plan.md` 与部分历史架构文档保留为设计参考，不再代表“编排能力尚未实现”的当前状态。

关联实现与资料：

- `server/src/pipeline/orchestrator.rs`
- `server/src/pipeline/handlers.rs`
- `server/src/pipeline/prompt_optimizations.rs`
- `server/src/main.rs`
- `server/src/ops/monitor.rs`
- `docker-compose.yml`
- `.github/workflows/ci.yml`
- `docs/backend-ops-monitoring.md`
- `docs/staging-db-rollback-drill.md`
- `docs/current-system-architecture.md`

## 2. 目标

1. 交付可供小范围真实用户使用的单实例封闭 Beta，保证核心创作任务不会静默丢失。
2. 让流水线在失败、重复操作、服务重启及外部生成异常后都能进入明确、可见、可处理的状态。
3. 建立发布前测试、回滚、备份恢复和告警的最低运营闭环。
4. 以真实项目验证完成率、人工介入率、审核重试率、耗时与单位可用产出的成本。
5. 在不扩大系统架构的前提下，形成是否进入下一阶段的可量化决策依据。

## 3. 非目标

- 不在本阶段引入多实例部署、分布式任务队列、消息代理或高可用架构。
- 不在本阶段从 SQLite 迁移至其他数据库。
- 不自动应用提示词优化建议；保持“系统建议，人工确认后应用”的工作方式。
- 不进行全面 UI 重设计，不为所有通知渠道补齐实现。
- 不以功能数量作为 Beta 成功标准。

## 4. 用户与角色

| 角色 | 核心诉求 | 本阶段责任 |
| --- | --- | --- |
| 创作者 | 连续完成创作流程，了解失败原因并能继续处理 | 发起任务、审核内容、执行授权的重试或人工处理 |
| 审核/运营人员 | 快速发现卡住或异常任务，保留处理痕迹 | 查看人工审核队列、处理异常、汇总反馈 |
| 发布负责人 | 可控发布、可回滚、可解释地判断 Beta 质量 | 管理环境、发布门禁、备份恢复和问题分级 |
| 研发与测试 | 稳定复现并修复问题 | 实现状态契约、自动化验证、维护运行手册 |

## 5. 产品需求

### FR-01：部署配置契约

系统必须区分 Demo/开发环境与生产环境，避免文档、Compose 默认值和服务启动校验相互矛盾。

- Demo/开发环境必须显式标识，允许使用仅限本地的演示配置。
- 生产环境不得因默认 JWT 密钥、宽松跨域配置或缺失的 API Key 加密密钥而启动为可用服务。
- 文档必须给出两条清晰路径：本地 Demo 启动与生产/预发布启动，并说明各自必填变量。
- 与外部模型服务相关的密钥必须避免以明文形式长期落库或输出到日志。

### FR-02：流水线生命周期完整性

流水线必须对启动、暂停、恢复、取消、重试、审核通过和审核拒绝定义一致的状态转换。

- 重复或并发操作不得产生重复推进、重复扣费、重复事件或不一致的最终状态。
- 每个状态转换必须记录可追踪的事件、时间、原因和操作者/来源。
- 重试次数耗尽、人工审核阻塞及可恢复失败必须呈现明确的下一步动作。
- 已有人工审核队列、失败记录和分镜持久化能力在本阶段不得回退。

### FR-03：服务重启与异常恢复契约

服务重启后，所有中断任务必须在用户可见的状态中收敛，禁止存在无提示的长期“运行中”孤儿任务。外部供应商请求是否可自动恢复取决于幂等性与供应商能力；无法安全恢复时，以失败归档、可控重试或人工审核为默认策略。

| 中断对象 | 重启后的必达结果 | 用户/运营可见信息 |
| --- | --- | --- |
| 排队中的 AI 任务 | 恢复排队，或明确失败并给出重试/人工处理入口 | 队列或失败原因、下一步动作 |
| 执行中的 AI 任务 | 由确定策略终止、重试或转人工审核 | 中断原因、已消耗步骤、可执行操作 |
| 执行中的图片/视频生成 | 对账本地记录与供应商结果；仅在具备幂等保证时自动重试 | 对账结果、退款/计费记录、重试资格 |
| 流水线运行 | 不能停留在虚假的运行中；须落到完成、失败、暂停或人工审核 | 失败步骤、事件记录、恢复路径 |

### FR-04：端到端回归验证

建立覆盖核心创作闭环的自动化回归矩阵，优先采用服务集成测试和关键用户路径 E2E 测试。

- 协作输入到流水线派发。
- 审核通过、审核拒绝、重试成功及重试耗尽。
- 图片/视频生成成功、供应商失败、计费/退款对账。
- 分镜及任务结果持久化后可重新读取。
- 暂停、恢复、取消和重复提交。
- 服务重启期间的任务收敛。
- SSE 断连后的重连与状态同步。

### FR-05：异常处理工作台

现有人工审核与事件记录必须成为运营人员处理异常的单一入口。

- 异常任务需要展示简短原因、失败步骤、最近事件和允许操作。
- 人工重试、放弃、标记已处理等动作必须留下审计记录。
- 不要求重做界面，但关键错误不应只存在于服务日志中。

### FR-06：发布与运营控制

封闭 Beta 需要可执行的预发布、发布、回滚、备份恢复和告警流程。

- 预发布环境配置与生产配置的差异必须可检查、可记录。
- 每次发布必须具备健康检查、版本记录和回滚路径。
- 数据备份、恢复、保留周期、RPO/RTO 目标须记录在运行手册中，并至少完成一次演练。
- 针对任务积压、失败率、重启恢复失败、外部供应商异常和存储空间建立阈值、责任人和响应步骤。

### FR-07：Beta 指标采集

现有流水线、事件、人工审核及用量数据必须能够支持每周 Beta 复盘。

- 指标的口径、数据来源、统计周期和负责人必须固定。
- 指标采集不得记录敏感密钥或不必要的用户内容。
- 允许先以固定报表或查询输出，不要求在本阶段建设完整的数据看板。

## 6. 非功能要求

| 维度 | 要求 |
| --- | --- |
| 可靠性 | 核心任务不得静默丢失；异常后必须进入可见的终态或可执行的处理中状态。 |
| 幂等性 | 生命周期控制、外部生成回调/对账和重试必须避免重复副作用。 |
| 数据完整性 | 流水线状态、事件、生成结果、分镜与计费处理记录应可关联追溯。 |
| 可观测性 | 健康状态、任务失败类别、积压、重启恢复结果和外部依赖异常可查询或告警。 |
| 安全性 | 生产密钥必须安全配置；保留 API Key 加密与外部请求 SSRF 防护。 |
| 工程质量 | 发布门禁覆盖前端构建与测试、服务端格式检查、静态检查、测试及迁移验证。 |

## 7. 验收标准

### P0 发布阻断项

1. 文档中的默认 Demo 启动方式仅能在显式 Demo/开发模式下工作；生产模式无法使用演示 JWT 密钥启动。
2. 生命周期状态转换具备集成测试：重复/并发提交控制操作后，不产生重复状态推进或重复事件。
3. 服务重启测试覆盖排队 AI 任务、执行中 AI 任务、执行中图片/视频生成及流水线运行；每个对象均在约定时间内进入已知状态，且没有孤儿“运行中”记录。
4. 至少一条完整集成或 E2E 路径从协作输入验证至分镜记录可读取，包含失败后的恢复或人工审核分支。
5. 服务端测试存在偶发失败时，必须完成根因定位与修复，或通过隔离策略证明并消除并发污染。
6. 发布前 CI 必须稳定执行核心前端与服务端检查；不允许以已知失败测试作为常态放行条件。
7. 当前架构与 Beta 执行基线文档完成更新，历史计划文档注明其参考性质。

### P1 Beta 运行项

1. 预发布完成至少一次数据库备份恢复和版本回滚演练，并记录结果、耗时与遗留问题。
2. 已定义备份频率、保留周期、目标 RPO/RTO、告警阈值及响应责任角色。
3. 任务失败、人工审核、供应商异常和恢复结果可按周导出或汇总。
4. 静态检查告警建立清零或递减门禁，逐步将 Rust Clippy 从报告项升级为阻断项。

## 8. 指标定义

| 指标 | 计算口径 | 数据来源 | 复盘频率 |
| --- | --- | --- | --- |
| 流水线自助完成率 | 已完成运行数 /（已完成 + 终态失败）运行数，不含用户主动取消 | 流水线运行与事件 | 每周 |
| 人工介入率 | 进入人工审核的运行或步骤数 / 已完成与终态失败总数 | 人工审核队列、事件 | 每周 |
| 审核重试率 | 发生审核后重试的次数 / 审核次数 | 审核与重试事件 | 每周 |
| 端到端耗时 | 从启动至完成的 P50、P90 | 流水线时间戳 | 每周 |
| 可用产出成本 | 已接受的图片/视频/分镜对应成本 / 被接受产出数 | 用量、生成与审核记录 | 每周 |
| 重启可恢复率 | 重启中断后在目标时间内收敛为已知状态的对象数 / 中断对象总数 | 恢复事件、任务状态 | 每次演练/发布 |
| 主要错误类别 | 按错误类型归类的 Top N 及趋势 | 失败事件、监控记录 | 每周 |

指标负责人由产品/运营角色指定，研发负责保证原始数据可取。

## 9. 推进计划与阶段门槛

| 阶段 | 建议周期 | 交付物 | 通过条件 |
| --- | --- | --- | --- |
| Phase 0：基线收敛 | 1-2 天 | 当前能力清单、部署配置契约、文档基线 | P0 风险被确认、Demo/生产路径可区分 |
| Phase 1：可靠性与测试 | 1 周 | 重启状态契约、测试修复、核心集成/E2E 回归 | P0 验收项 1-6 通过 |
| Phase 2：预发布验证 | 1 周 | 备份恢复与回滚演练、告警与运行手册、内部试用 | 演练成功，关键问题有处置结论 |
| Phase 3：封闭 Beta | 1-2 周 | 5-10 个真实项目、每周指标报告、问题分级清单 | 累计至少 30 次流水线运行并完成复盘 |

建议的 Beta 退出门槛（首轮基线，可根据样本质量校准）：

- 无安全事故、数据丢失或未知终态任务。
- P0 验收项全部通过，且备份恢复、版本回滚各完成至少一次演练。
- 流水线自助完成率不低于 85%。
- 人工介入率不高于 20%，超出时必须能归因到明确的产品或供应商问题。
- 所有高优问题都有负责人、处置状态和是否影响扩大的结论。

## 11. 风险与决策原则

| 风险 | 影响 | 处理原则 |
| --- | --- | --- |
| 外部供应商请求不可恢复或不具幂等性 | 重试可能造成重复成本或重复产出 | 优先对账；不能安全重试时转人工审核并保留计费痕迹 |
| SQLite 与单实例容量边界 | 并发增长时可用性与吞吐受限 | 作为 Beta 已知边界监控，达到阈值后再启动架构演进 |
| 自动化测试不稳定 | 发布结果不可预测 | 测试隔离与稳定性为 P0，不以偶发通过替代修复 |
| 外部模型成本、限流和质量波动 | 完成率与成本失真 | 用错误分类、耗时和可用产出成本做周度归因 |
| 文档与实现脱节 | 错误决策或错误部署 | 本 PRD 和运行手册作为执行基线，历史文档明确标注状态 |

# Woohoo 真实 Staging 演练与内部试用准入 PRD

版本：v1.2  
日期：2026-08-24  
状态：Phase C 前置准备已完成，待真实 staging 演练  
前序版本：[v1.1 预发布演练与封闭 Beta 准入 PRD](../v1.1/closed-beta-stabilization-prd-v1.1.md)  
适用阶段：候选发布、真实 staging 演练、内部试用与外部封闭 Beta 准入

## 1. 版本背景与当前决策

v1.1 的 Phase A/B 已完成：AI 历史状态兼容、非法状态收敛、重复恢复幂等、Pipeline `recovery_failed` SQLite 幂等测试、连续 5 轮服务端全量测试，以及前端、Rust 和三套 Compose 的本地/CI 门禁均已完成。

当前唯一正确的下一步是真实 staging 演练。此阶段要验证的是候选版本能否安全读取真实旧数据，以及出现问题时能否在可接受时间内恢复快照并启动上一稳定版本。它不能由本地演练、单元测试或 Compose 解析替代。

发布决策：不回退 v1.1 的实现；不扩大到内部试用或外部封闭 Beta；先完成本 PRD 的 Phase C。只有 Phase C 通过，才能启动 Phase D 内部试用。

### 1.1 当前实施状态（截至 2026-08-24）

本版本的仓库内准备工作已经完成，但真实 staging 演练尚未开始，当前不能宣称 v1.2 已完成：

| --- | --- | --- |

| 候选/上一稳定版本及制品 | 待登记 | 需要在发布窗口记录 commit/tag、制品位置、启动方式和实际 CI 运行链接。 |

## 2. 目标与非目标

### 2.1 目标

1. 固定可复现的候选版本与上一稳定版本，并确保二者制品均可启动。
2. 在真实 staging 上完成“快照 -> 候选版本 -> 冒烟 -> 恢复快照 -> 上一稳定版本”的跨版本回滚演练。
3. 留存足以支持 Go/No-Go 决策的演练证据、时间数据和异常结论。
4. 演练通过后，以受控范围启动内部试用，验证真实创作、异常处理和运营流程。

### 2.2 非目标

- 不在本版本增加创作、生成、编排或架构功能。
- 不以演练成功直接等同于外部封闭 Beta 准入。
- 不在 staging 使用演示 JWT、宽松 CORS 或未受保护的 API Key 加密密钥。
- 不在发现 P0/P1 或未解释数据差异时现场修补后继续扩大范围。

## 3. 准入范围与角色

| 对象 | 本版本范围 | 责任角色 |
| --- | --- | --- |
| 候选版本 | 已通过本地门禁的 commit/tag 和对应可启动制品 | 研发、发布负责人 |
| 上一稳定版本 | 已确认可回切的 commit/tag 和对应可启动制品 | 研发、发布负责人 |
| staging 数据 | 当前使用的 SQLite 主库、WAL、SHM 及快照目录 | 运维、发布负责人 |
| 演练执行 | 快照、部署、健康检查、业务冒烟、恢复、回切 | 运维、测试、发布负责人 |
| 内部试用 | 经授权的内部用户和受控测试项目 | 产品、运营、测试 |

发布负责人拥有演练停止和 Go/No-Go 决策权。没有其记录确认，不得把演练或内部试用标记为通过。

## 4. Phase C：真实 Staging 演练

### 4.1 演练前置条件

以下条件必须全部满足，才能开始操作：

1. 候选版本 commit/tag、上一稳定版本 commit/tag、两个制品位置均已记录并可启动。
2. 候选版本的实际 CI 运行已通过，链接或流水线编号已记录；不得仅引用本地验证。
3. staging 写入窗口已冻结，确认没有旧 server 或后台任务仍在写入数据库。
4. 已执行 `node scripts/staging-db-rollback-drill.mjs status`，确认 `DATABASE_URL`、数据库路径和现有文件均符合预期。
5. 已确认快照存放空间、演练操作人、回滚权限、健康检查地址和停机通知对象。
6. 生产环境变量来自受保护配置，且满足 [部署说明](../../../docker-deploy.md) 的 JWT、CORS 与加密密钥契约。

任一条件不满足：停止，不生成候选部署，不以临时口头承诺替代记录。

### 4.2 执行步骤

1. **建立演练记录。** 记录开始时间、环境、候选/稳定版本、数据库路径、执行人和观察人。
2. **冻结写入并生成快照。** 停止当前 server 与可能写入的后台进程，执行 `node scripts/staging-db-rollback-drill.mjs snapshot pre-release`；保存 `snapshotDir`、`metadata.json` 和文件清单。
3. **部署候选版本。** 用 staging 的实际部署制品启动候选版本；保存启动日志，确认数据库迁移/补数报告没有新的兼容问题。
4. **候选版本冒烟。** 检查 `/health`；调用 `/api/workspace/bootstrap`；读取至少一个已有项目，确认对话、资产、agent 配置和任务恢复不会立即报错。
5. **执行回滚。** 停止候选版本，执行 `node scripts/staging-db-rollback-drill.mjs restore <snapshotDir>`；保留恢复命令结果和脚本创建的 `_pre_restore_<timestamp>` 备份目录。
6. **切回上一稳定版本。** 启动上一稳定版本，重复健康检查与已有项目读取；确认不存在缺表、缺列、外键错误或不可读取的数据。
7. **收尾。** 恢复到发布负责人决定的安全版本，解除写入冻结；归档日志、快照元数据、健康检查和结论。

详细操作以 [staging 数据库回滚演练手册](../../../staging-db-rollback-drill.md) 为准；本 PRD 定义准入与决策口径。

### 4.3 演练验收

| 检查项 | 通过标准 | 必留证据 |
| --- | --- | --- |
| 快照完整性 | 主库、WAL、SHM 和 `metadata.json` 均已生成，路径可访问 | `snapshotDir`、文件清单、生成时间 |
| 候选启动 | 候选版本启动成功，`/health` 返回成功，日志无新迁移兼容错误 | 版本标识、日志片段、健康检查结果 |
| 旧数据可读 | workspace bootstrap 与至少一个已有项目读取成功 | 接口结果摘要、项目标识、测试人 |
| 回滚恢复 | 快照恢复完成，上一稳定版本重新启动成功 | restore 输出、稳定版本日志、健康检查结果 |
| 回滚后数据可读 | 回滚后旧项目的对话、资产、agent 配置可读 | 冒烟结果、差异说明（如有） |
| 数据一致性 | 无未解释的数据丢失、结构错误或不可读记录 | 结论、异常单号或无异常声明 |

### 4.4 停止、回退与事故规则

| 触发条件 | 立即动作 | 后续决策 |
| --- | --- | --- |
| 候选版本无法启动或健康检查失败 | 停止候选；恢复快照；切回上一稳定版本 | No-Go，创建缺陷并重新验证。 |
| 迁移/补数日志出现新兼容错误 | 不执行扩大验证；恢复快照并回切 | No-Go，先修复兼容问题。 |
| 旧项目或关键数据不可读 | 立即回滚；保留读失败证据 | 按 P0/P1 处置，禁止内部试用。 |
| 回滚后稳定版本不可启动或数据不可读 | 保持写入冻结；启动事故响应 | P0，禁止发布，完成根因与恢复确认后再排期。 |
| 非阻断告警但无数据风险 | 记录并评估影响 | 发布负责人可决定整改后重演或带风险进入内部试用。 |

回退对象是候选部署与 staging 数据快照。不得在未确认快照存在且可恢复前，删除数据卷或执行不可逆迁移操作。

## 5. Phase C 决策与交付

### 5.1 Go/No-Go

**Go（进入内部试用）**：第 4.3 节六项验收全部通过；没有 P0/P1 未决问题；候选版本、稳定版本、快照路径与全部证据可追溯。

**No-Go（保持 staging 或回切稳定版本）**：任意验收项失败、发生回滚失败、存在未解释数据差异，或演练记录不完整。No-Go 不是要求整体回退 v1.1，而是阻断扩大范围，修复具体问题后重新完整演练。

### 5.2 演练记录模板

每次演练在 `docs/prd/closed-beta-stabilization/v1.2/evidence/` 建立一份以日期命名的 Markdown 记录，至少填写：

可直接复制 [演练记录模板](evidence/staging-drill-record-template.md)，再以 `YYYY-MM-DD-<environment>.md` 命名。模板中的占位符必须在演练结束前替换或明确标记为“不适用”。

| 字段 | 内容 |
| --- | --- |
| 演练时间与环境 | 开始/结束时间、staging 标识 |
| 版本 | 候选 commit/tag、上一稳定 commit/tag、制品标识 |
| 操作信息 | 执行人、观察人、发布负责人 |
| 数据库与快照 | `DATABASE_URL` 脱敏摘要、`snapshotDir`、文件清单 |
| 候选验证 | 迁移日志、健康检查、bootstrap、已有项目读取结果 |
| 回滚验证 | restore 输出、稳定版本健康检查、已有项目读取结果 |
| 时间指标 | 快照耗时、候选启动耗时、回滚恢复耗时、总窗口 |
| 结论 | Go/No-Go、遗留风险、问题单与负责人 |

不得把密钥、完整连接凭据、用户内容或未脱敏日志写入该记录。

## 6. Phase D：内部试用

### 6.1 启动条件

仅在 Phase C 获得 Go 后启动。第一轮内部试用限定为内部授权用户和可回收测试项目，不面向外部用户扩容。

### 6.2 验证范围

每位试用者至少覆盖一个完整项目中的以下能力：

1. 协作输入到流水线派发与结果读取。
2. 审核通过或拒绝，以及一次授权重试或人工处理。
3. 图片/视频或其他外部生成失败时的可见错误与后续操作。
4. 任务异常、服务重启或状态恢复后的可见状态与恢复路径。
5. 运营人员从事件/人工审核入口定位问题、留痕并完成处置。

### 6.3 内部试用周期与指标

建议连续运行 5 个工作日或至少完成 10 个内部真实项目，以先达到者为准。每日汇总：

| 指标 | 口径 | 升级条件 |
| --- | --- | --- |
| 核心流程完成率 | 完成项目 / 已结束项目（不含用户主动取消） | 明显低于 85% 或连续两日下降。 |
| 人工介入率 | 进入人工审核或人工恢复的项目 / 已结束项目 | 高于 20% 且无法归因。 |
| 未知终态任务 | 无明确下一步动作的任务数 | 任意出现即按 P0 调查。 |
| 恢复异常 | 重启/恢复后状态、事件或数据不一致的次数 | 任意数据不一致即暂停试用。 |
| 外部依赖异常 | 供应商失败、限流、重复计费或对账异常 | 按影响分级并记录处置结果。 |

## 7. 外部封闭 Beta 准入

外部封闭 Beta 不属于本版本的自动产出。只有以下条件同时成立，才可另行作 Go 决策：

1. Phase C 演练通过且证据完整。
2. 内部试用达到约定样本，核心流程完成率不低于 85%，且无 P0/P1 未决问题。
3. 未知终态任务为零；恢复异常和供应商问题均有明确归因及处理记录。
4. 运营已能按周汇总失败、人工审核、恢复结果和成本数据。
5. 发布负责人、产品、测试、运维对接入范围、支持方式和回退责任留痕确认。

满足条件后，外部首批仍限定为 5-10 个真实项目，并沿用本 PRD 的停止和回退规则。

## 8. 完成定义

本 PRD 在以下条件全部满足时完成：

1. 真实 staging 演练按记录模板留存，结论为 Go。
2. 内部试用完成约定周期/样本并产出指标与问题清单。
3. 外部封闭 Beta 已形成有证据的 Go 或 No-Go 决策；若 No-Go，已明确责任人与下一版修复范围。

在完成前，系统状态应持续标记为“真实 staging 演练中”或“内部试用中”，不得标记为“已可外部封闭 Beta”。

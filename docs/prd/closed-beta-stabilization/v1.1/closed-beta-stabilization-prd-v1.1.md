# Woohoo 预发布演练与封闭 Beta 准入 PRD

版本：v1.1  
日期：2026-08-24  
状态：Phase A/B 已实施，待真实 staging 演练  
前序版本：[v1.0 稳定化与发布准备 PRD](../v1.0/closed-beta-stabilization-prd-v1.0.md)  
适用阶段：稳定化收口、预发布演练、内部试用与封闭 Beta 准入

## 1. 背景与版本关系

v1.0 已完成 AI 任务重启恢复、孤儿任务收敛、Pipeline 恢复失败事件与可重试状态、生产启动配置校验、Demo/生产 Compose 拆分，以及相关运行文档同步。服务端、前端、构建与本地隔离数据库回滚演练均已有通过记录。

本版本不回退上述实现，也不以新增功能替代收口工作。审计后仍有三项发布前风险需要处理：

1. 历史 `ai_tasks` 状态可能以 `Queued`、`Running` 等大小写形式存在；状态解析可兼容，但恢复 SQL 仅匹配小写时，重启后可能无法把这类记录收敛到可见状态。
2. AI/Pipeline 重启恢复缺少 SQLite 集成测试，尤其缺少 Pipeline `recovery_failed` 事件的幂等性证明。
3. SQLite 测试连接池调整已经通过一次全量验证，但需要多轮验证以排除偶发超时。

当前发布决策：保持现有稳定化实现，不回退；本 PRD 的 Phase A 和 Phase B 已完成代码、测试与门禁收口，下一步进入真实 staging 演练准备。未完成并通过 Phase C 前，不进入内部试用或外部封闭 Beta。

## 2. 目标

1. 让历史大小写状态的 AI 任务在服务重启后也能收敛为明确、可操作的状态。
2. 用可重复执行的 SQLite 集成测试覆盖 AI 与 Pipeline 的重启恢复和事件幂等性。
3. 建立可执行的合并门禁与预发布准入证据，避免以单次本地通过代替稳定性结论。
4. 在真实 staging 完成备份恢复和跨版本回滚演练，再进入内部试用和小范围外部封闭 Beta。

## 3. 非目标

- 不回退 v1.0 已实施的重启恢复、生产配置校验或 Compose 拆分。
- 不新增多实例、分布式队列、消息代理或数据库迁移等架构工作。
- 不在本版本扩展新的创作、生成或编排能力。
- 不把本地回滚演练视为真实 staging 跨版本回滚的替代品。

## 5. 产品与工程需求

### FR-01：历史 AI 任务状态兼容与收敛

服务启动恢复必须将历史数据中的状态值视为不可信输入，并采用统一的规范化比较策略。

- 恢复查询、更新条件和状态机判断必须对 `queued/Queued/QUEUED`、`running/Running/RUNNING` 表现一致。
- 对无法映射的状态，必须记录可检索的恢复失败原因，并转入明确的失败或人工处理状态；不得静默保留为运行中。
- 恢复后数据库中不得保留本次应处理范围内的 `queued` 或 `running` 大小写变体。
- 重复启动或重复调用恢复逻辑不得重复推进任务、重复产生副作用或覆盖已终态记录。

### FR-02：AI 任务重启恢复集成测试

新增基于临时 SQLite 数据库的集成测试，直接验证持久化状态和恢复后的用户可见结果。

至少覆盖：

| 场景 | 前置数据 | 期望结果 |
| --- | --- | --- |
| 排队任务恢复 | `queued` 及 `Queued` 任务 | 进入约定的排队恢复或失败可重试状态，字段与事件一致。 |
| 执行中任务恢复 | `running` 及 `Running` 任务 | 进入确定的失败、可重试或人工处理状态，包含中断原因。 |
| 已终态任务 | `completed/failed/cancelled` 任务 | 不被改写，不新增恢复副作用。 |
| 重复恢复 | 对同一数据库连续执行恢复两次 | 第二次不改变终态，不重复写入事件或计数。 |
| 非法历史状态 | 无法解析的状态值 | 有可诊断失败信息，不保留伪运行状态。 |

### FR-03：Pipeline 恢复失败事件幂等性

当 Pipeline 的恢复步骤发生异常时，系统必须留下一个可重试的失败状态和唯一的失败事件。

- 同一恢复异常仅创建一条语义等价的 `recovery_failed` 事件；重复恢复不得按次数重复写入。
- 运行及步骤状态必须与事件一致，且前端/运营可获得失败步骤、原因和允许操作。
- 可重试状态必须明确区别于不可恢复的终态失败；重试次数和审计信息不得被重复恢复污染。
- 测试必须在 SQLite 上验证事件记录数、状态写回和第二次调用的无副作用行为。

### FR-04：SQLite 测试稳定性

连接池调整后的验证不能只依赖单次全量通过。

- 在相同代码与依赖版本下，服务端全量测试至少连续执行 5 次。
- 任一次超时、锁冲突、随机失败或依赖执行顺序的失败均视为未通过，必须保留日志并定位原因。
- 测试不得依赖工作区共享数据库、固定端口残留或前一次测试留下的状态。
- 若 CI 与本地执行参数不同，CI 必须采用不弱于本地的隔离策略。

### FR-05：发布门禁与证据

候选发布版本必须具备可追溯的质量证据。

- 服务端格式检查、测试、前端测试、lint、类型检查和构建必须通过。
- 新增恢复集成测试必须纳入常规测试命令或 CI，不允许仅人工运行。
- Compose 配置解析必须分别覆盖 Demo/开发和生产配置。
- 每次候选版本必须记录 commit/tag、检查结果、环境变量模板版本和已知风险。

## 6. 实施计划与阶段门槛

### Phase A：代码与测试收口（已完成）

交付：状态兼容修复、AI/Pipeline SQLite 集成测试、稳定性验证记录。

通过条件：

1. 恢复 SQL 与状态判断已统一规范化，覆盖历史大小写状态。
2. AI 与 Pipeline 的新增集成测试在本地和 CI 均可运行。
3. 连续 5 次服务端全量测试全部通过，无超时和偶发失败。
4. 变更经过代码审查，未引入新的状态机或数据迁移风险。

未满足任一条件：不进入 Phase B，不回退 v1.0；继续修复并保留失败证据。

### Phase B：CI 与候选版本门禁（实施完成，候选证据待补齐）

交付：候选版本、完整检查记录、发布说明和 staging 演练预约/窗口。

通过条件：

1. CI 全部必需检查通过，新增恢复测试在其中执行。
2. Docker Compose Demo/开发与生产配置均可解析，生产必填密钥校验仍有效。
3. 已确定候选版本和上一稳定版本的 commit/tag，且二者制品均可启动。
4. 已按 [staging 数据库回滚演练手册](../../../staging-db-rollback-drill.md) 准备快照位置、操作人和回滚权限。

未满足任一条件：候选版本不得部署到 staging。

### Phase C：真实 Staging 备份恢复与跨版本回滚演练（待完成）

交付：一次可审计的真实环境演练记录。

执行顺序：

1. 停止 staging 写入，记录当前数据库路径、候选版本和上一稳定版本。
2. 生成迁移前 SQLite 主库、WAL 和 SHM 的完整快照。
3. 启动候选版本，检查迁移/补数报告、`/health`、工作区 bootstrap 和至少一个已有项目的读取。
4. 在演练窗口内执行恢复快照，切回上一稳定版本。
5. 再次验证健康检查、已有项目、对话、资产和 agent 配置可读。
6. 记录耗时、命令输出摘要、异常、数据差异及结论。

通过条件：候选版本能读取旧数据；恢复快照后上一稳定版本能启动且业务数据可读；无未解释的数据差异。

失败处理：立即停止扩大范围，保持或切回上一稳定版本；按第 8 节判断是否需要代码修复或环境修复。

### Phase D：内部试用与封闭 Beta（未开始）

内部试用：先由内部用户完成核心创作链路、失败处理、重试、审核和重启恢复验证，持续观察告警与事件。

外部封闭 Beta：仅在内部试用通过且无 P0/P1 未决问题后，按 5-10 个真实项目的小范围接入。每周复盘完成率、人工介入率、重启恢复结果、供应商异常和可用产出成本。

## 7. 验收标准

### P0 准入标准

1. 重启恢复后，数据库中没有属于本次恢复范围的 `queued/running/Queued/Running` 遗留记录。
2. AI 恢复失败状态、原因、可执行后续动作与持久化记录一致；重复恢复没有二次副作用。
3. Pipeline 步骤恢复异常后，运行与步骤均进入约定的可重试失败状态；每个异常仅有一条 `recovery_failed` 事件。
4. 服务端全量测试连续 5 次通过；前端测试、lint、类型检查、构建及 Rust 格式检查通过。
5. CI 对上述检查均设为候选版本必需门禁。
6. 生产配置不能用演示 JWT、宽松 CORS 或缺失 API Key 加密密钥启动为可用服务。

### P1 准入标准

1. 真实 staging 已完成备份恢复和跨版本回滚演练，并保存完整记录。
2. 候选版本与上一稳定版本均能在相应数据库快照上通过健康检查和业务冒烟。
3. 内部试用完成至少一轮核心创作与异常处理验证，无 P0/P1 未决问题。
4. Beta 运营已具备失败、人工审核、供应商异常与恢复结果的周度汇总方式。

## 8. 回退与问题处置策略

| 情况 | 决策 | 处置 |
| --- | --- | --- |
| Phase A 发现状态收敛或幂等缺陷 | 修复 | 保持 v1.0 已实施能力，修正兼容逻辑并补回归测试。 |
| 测试出现偶发失败或超时 | 修复 | 阻断候选发布，保留日志并定位测试隔离、连接池或共享状态问题。 |
| staging 候选版本启动/读旧数据失败 | 回退 | 恢复演练前快照并启动上一稳定版本，记录故障和数据差异。 |
| staging 演练成功但内部试用出现 P0/P1 | 暂停扩大 | 修复后重新执行受影响的演练或验证，不直接扩大外部 Beta。 |
| 外部 Beta 出现数据丢失、安全问题或未知终态任务 | 紧急回退 | 停止写入和新增接入，按演练手册恢复，启动事故复盘。 |

回退只针对候选版本或新增修复；v1.0 的稳定化实现不因测试覆盖不足而整体撤销。只有出现已证实的 P0 数据完整性或安全回归，才评估回退对应实现。

## 9. Go/No-Go 决策

| 决策点 | Go 条件 | No-Go 条件 |
| --- | --- | --- |
| 进入 staging | Phase A、B 全部通过 | 任一 P0 代码、测试或 CI 门禁未通过。 |
| 进入内部试用 | staging 演练通过，回退路径已验证 | 候选版不能读旧数据、回退失败或存在未解释数据差异。 |
| 进入外部封闭 Beta | 内部试用通过，无 P0/P1 未决，运营周报可产出 | 关键链路不稳定、告警/运营不可处理或存在未关闭高优问题。 |
| 扩大 Beta 范围 | 至少完成一轮周度复盘，指标无恶化趋势 | 出现数据丢失、未知终态、重大安全问题或完成率明显恶化。 |

发布负责人拥有最终 Go/No-Go 决策权；研发、测试、运维和产品必须对各自验收证据签字或留痕。

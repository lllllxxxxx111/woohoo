# 对话驱动多智能体协同编排 PRD（草案）

版本：v0.1  
日期：2026-04-14  
适用范围：项目内对话区 -> 多智能体协同 -> 工作区执行

## 1. 背景

当前系统已经具备三块基础能力：

1. 项目内对话可走服务端任务模式，支持流式返回、落库、刷新恢复。
2. `workflow guard` 已可用于信息补齐和确认继续。
3. `Outline` 已可手动发起 `pipeline run` 进入工作区编排。

但当前仍缺少一层关键能力：

1. 默认助理只能继续聊天，不能在“信息成熟”后自动切换到多智能体协同。
2. 智能体之间没有真正的 `@` 路由、提问队列和阻塞解除机制。
3. 讨论与执行之间没有清晰门槛，无法自然从对话区切入工作区。
4. 缺少循环检测，容易出现多个智能体来回追问、无进展复读的问题。

本 PRD 要解决的是：  
用户先用自然语言提出创作想法；当信息达到可分工程度后，系统自动拉起多智能体协同；智能体先在对话区补齐问题、消除阻塞，再在条件满足后步入工作区执行。

## 2. 产品目标

### 2.1 目标

1. 让默认助理在项目内对话中具备“识别成熟度 -> 发起协同 -> 管理讨论 -> 切入工作区”的能力。
2. 允许智能体基于依赖关系向上游智能体、编导、默认助理或用户发问，而不是只允许问编导。
3. 所有被 `@` 的智能体按队列顺序回复，避免并发抢答和上下文混乱。
4. 只有当关键问题收敛后，才进入工作区执行；若仍有阻塞，则继续停留在对话区。
5. 每 5 轮对话做一次循环检测，防止死循环、复读和无进展反问。

### 2.2 非目标

1. 本期不做“任意智能体自由群聊”的开放式聊天室。
2. 本期不做全局聊天场景的自动协同，仅限项目内对话。
3. 本期不要求一次覆盖全部流程类型，优先覆盖 `大纲 -> 剧本 -> 章节/分镜` 主链路。
4. 本期不做分布式多实例协同调度，默认单服务实例内落地。

## 3. 用户场景

### 3.1 主场景

1. 用户在项目内对话区输入一个创作想法。
2. 默认助理先和用户沟通，补齐最关键的创作约束。
3. 当默认助理判断信息足够启动协同时，自动 `@编导智能体`。
4. 编导智能体把任务拆给 `@大纲`、`@剧本`、`@角色`、`@分镜` 等智能体。
5. 某个智能体如果没有疑问，则进入 `ready`，等待步入工作区。
6. 某个智能体如果有疑问，可以询问它的上游依赖智能体、编导、默认助理或用户。
7. 被 `@` 的智能体按顺序回复，直到关键智能体不再阻塞。
8. 当达到入场条件后，系统自动把对应任务落到工作区，开始真正执行。

### 3.2 示例

1. 用户说：“我想做一个悬疑反转短剧，节奏快，面向 18-30 岁女性用户。”
2. 默认助理先补充问题：时长、题材边界、核心情绪、是否偏现实。
3. 信息足够后，默认助理触发协同，编导分派：
   - `@大纲` 明确故事走向和核心反转
   - `@角色` 设计主要人物关系
   - `@剧本` 暂缓，等待大纲稳定
4. `剧本` 发现剧情走向不明，可以直接 `@大纲` 追问，而不是只能问编导。
5. `大纲` 回复后，`剧本` 状态从 `blocked` 变成 `ready`。
6. 当大纲无疑问且通过编导检查后，工作区自动进入 `Outline` 阶段。

## 4. 角色定义

1. 默认助理
   - 面向用户的主入口
   - 负责识别需求成熟度
   - 负责向用户解释当前协同状态
   - 在必要时向用户收口问题

2. 编导智能体
   - 协同编排者
   - 负责拆任务、分配角色、判断哪些任务可入工作区
   - 不必回答所有领域问题，但负责维持全局一致性

3. 领域智能体
   - 例如：大纲、剧本、角色、分镜、视频提示词
   - 负责本专业范围的产出和追问

4. 用户
   - 最终决策者
   - 当系统检测到关键信息缺失或循环时，负责裁决

## 5. 核心概念

### 5.1 协同会话（Collaboration Session）

在一个项目会话内，由默认助理触发的一段多智能体协同讨论，包含：

1. 当前目标
2. 已补齐约束
3. 待分派任务
4. 智能体状态
5. 阻塞问题
6. 循环检测信息

### 5.2 任务卡（Assignment）

编导分配给某个智能体的一条任务，包含：

1. `agent_id`
2. `task_type`
3. `goal`
4. `inputs`
5. `depends_on`
6. `status`
7. `blocking_questions`

### 5.3 上游依赖

智能体可向其依赖来源发问，而不是只允许问编导。  
例如：

1. `剧本` 可问 `大纲`
2. `分镜` 可问 `剧本`
3. `视频提示词` 可问 `分镜`
4. 任一智能体都可在必要时问 `编导`、默认助理或用户

但默认规则是：

1. 优先问最近上游依赖
2. 上游无法回答时再升级到编导
3. 仍无法回答时再升级到默认助理或用户

## 6. 目标流程

### 6.1 阶段划分

1. `discovery`
   - 默认助理与用户澄清需求
2. `delegating`
   - 默认助理触发编导，编导拆任务并派发
3. `resolving_questions`
   - 智能体之间按依赖关系提问、回答、消除阻塞
4. `workspace_admission`
   - 编导判断哪些任务已满足入工作区条件
5. `workspace_execution`
   - 工作区创建或推进真实 `pipeline run`
6. `completed`
   - 协同完成
7. `halted`
   - 因循环、超时、冲突或人工中止而暂停

### 6.2 端到端行为

1. 用户发起创意需求。
2. 默认助理持续收集关键信息。
3. 达到“可分工阈值”后，默认助理创建 `collaboration session`。
4. 编导生成一组任务卡。
5. 被 `@` 的智能体进入回复队列。
6. 智能体可声明：
   - `ready`
   - `question`
   - `blocked`
   - `done`
7. 如果有 `question`，系统按队列安排被询问方回复。
8. 每 5 轮运行一次循环检测。
9. 当关键任务状态达到 `ready` 且无关键阻塞时，编导提交工作区入场。
10. 工作区开始真实执行，协同会话转为跟踪态。

## 7. 自动入工作区规则

### 7.1 入场前提

只有同时满足以下条件，才允许自动步入工作区：

1. 已创建 `collaboration session`
2. 编导已完成任务拆解
3. 关键依赖链上没有 `blocked` 状态
4. 关键字段已满足最小要求
5. 没有未解决的高优先级问题
6. 编导明确给出 `admit_to_workspace = true`

### 7.2 大纲阶段最小要求（首期建议）

以 `Outline` 为首期入场门槛，至少要求：

1. 题材/类型明确
2. 核心故事方向明确
3. 目标受众明确
4. 体量约束明确（例如：短剧/短视频、篇幅、时长）
5. 大纲智能体状态为 `ready`

### 7.3 不入场情形

以下情况必须继续留在对话区：

1. 大纲方向仍冲突
2. 关键角色关系尚未稳定
3. 核心时长或题材边界缺失
4. 连续追问但无新信息
5. 用户尚未确认关键分歧

## 8. 智能体对话与排队规则

### 8.1 回复队列

系统维护一个显式的 `reply_queue`：

1. 被 `@` 的智能体进入队列尾部
2. 同一时间只允许一个“当前发言者”
3. 后续回复必须等待前一个发言结束
4. 如果一个回复中又 `@` 了新的智能体，新智能体进入队列尾部

### 8.2 优先级

默认优先级建议：

1. 解除阻塞的问题 > 普通补充说明
2. 上游依赖回复 > 下游任务汇报
3. 用户裁决 > 智能体内部讨论
4. 编导的状态变更/分派指令 > 普通讨论

### 8.3 允许的提问目标

智能体可提问给：

1. 最近上游依赖智能体
2. 编导
3. 默认助理
4. 用户

不建议直接提问给：

1. 与自己无依赖关系的平级智能体
2. 明显下游的执行智能体
3. 已经被判定无法回答同一问题的对象

## 9. 循环防护

### 9.1 检测频率

每累计 5 轮代理对话，必须执行一次循环检测。

“1 轮”定义为：一个智能体或默认助理完成一次有效回复。  
用户回复不计入循环轮次，但会重置部分循环判断。

### 9.2 检测信号

出现以下任一信号，判定为高循环风险：

1. 最近 5 轮中问题指纹重复率高
2. 最近 5 轮没有新增结构化约束
3. 最近 5 轮没有任何任务状态变化
4. 同一问题在两个或多个智能体之间来回转发
5. 最近 5 轮仅做同义复述，无新结论

### 9.3 处置策略

1. 第一次命中：生成“循环风险提示”，要求当前责任智能体改写为明确问题。
2. 第二次连续命中：升级给编导，由编导汇总冲突并重新拆解任务。
3. 第三次连续命中：升级给默认助理，请求用户裁决。
4. 超过阈值仍无解：将协同会话标记为 `halted`，停止自动推进。

### 9.4 硬限制

1. 同一问题最多追问 3 次
2. 同一对智能体之间同一主题最多往返 2 轮
3. 单次协同会话最多自动讨论 20 轮
4. 达到上限后必须请求用户决策或人工接管

## 10. 状态机

### 10.1 协同会话状态

1. `discovery`
2. `delegating`
3. `resolving_questions`
4. `workspace_admission`
5. `workspace_execution`
6. `completed`
7. `halted`
8. `cancelled`

### 10.2 任务卡状态

1. `idle`
2. `assigned`
3. `questioning`
4. `ready`
5. `running`
6. `blocked`
7. `done`
8. `failed`

### 10.3 关键迁移

1. `idle -> assigned`
   - 编导创建任务卡
2. `assigned -> questioning`
   - 智能体提出问题
3. `assigned -> ready`
   - 智能体确认无阻塞
4. `questioning -> blocked`
   - 问题需要上游或用户回答
5. `blocked -> ready`
   - 阻塞解除
6. `ready -> running`
   - 入工作区并开始执行
7. `running -> done`
   - 工作区执行完成

## 11. 功能需求（FR）

1. FR-01：默认助理可在项目内对话中判断是否达到“协同启动阈值”。
2. FR-02：达到阈值时，系统自动创建 `collaboration session`。
3. FR-03：编导智能体可生成任务卡并分派给多个领域智能体。
4. FR-04：领域智能体可向上游依赖、编导、默认助理或用户发问。
5. FR-05：所有被 `@` 的智能体按统一队列顺序回复。
6. FR-06：当关键任务进入 `ready` 且无关键阻塞时，系统可自动步入工作区。
7. FR-07：若仍有问题，则必须继续留在对话区，不得误入工作区。
8. FR-08：每 5 轮对话必须运行循环检测。
9. FR-09：循环达到阈值后，必须自动暂停并升级给用户或人工接管。
10. FR-10：所有协同状态、提问链、队列和入场决策都必须可追踪、可落库、可恢复。

## 12. 非功能需求（NFR）

1. NFR-01：刷新页面后，协同会话状态、队列和阻塞问题可恢复。
2. NFR-02：不允许同一轮出现多个智能体并发抢答导致上下文错乱。
3. NFR-03：所有自动入工作区决策必须可解释，能看到“为什么入场/为什么未入场”。
4. NFR-04：循环检测不可 silent failure，必须留下事件记录。
5. NFR-05：协同会话故障后，10 分钟内可通过日志和事件定位到责任智能体与问题链路。

## 13. 数据模型建议

### 13.1 新增表

1. `collaboration_sessions`

   - `conversation_id`

   - `admission_decision_json`
   - `loop_status_json`
   - `created_at`
   - `updated_at`

2. `collaboration_assignments`
   - `id`
   - `session_id`
   - `agent_id`
   - `task_type`
   - `goal`
   - `input_json`
   - `depends_on_json`
   - `status`
   - `blocking_question_count`
   - `last_question_fingerprint`

   - `updated_at`

3. `collaboration_messages`
   - `id`

   - `source_agent_id`

4. `collaboration_events`
   - `id`
   - `session_id`
   - `event_type`
   - `payload_json`
   - `created_at`

### 13.2 复用现有表

1. `messages`
   - 继续承载面向用户展示的对话消息
2. `pipeline_runs`
   - 承载真正进入工作区后的执行 run
3. `pipeline_run_steps`
   - 承载工作区内正式步骤
4. `agents` / `project_agent_assignments`
   - 承载智能体定义和项目绑定

## 14. API 与契约建议

1. `POST /api/collaboration/sessions`
   - 从项目内对话启动协同
2. `GET /api/collaboration/sessions/{id}`
   - 返回协同会话状态、任务卡、阻塞问题、当前队列
3. `POST /api/collaboration/sessions/{id}/dispatch`
   - 编导生成或更新任务分派
4. `POST /api/collaboration/sessions/{id}/messages`
   - 某个智能体发送 `assign/question/answer/status`
5. `POST /api/collaboration/sessions/{id}/loop-check`
   - 主动触发循环检测
6. `POST /api/collaboration/sessions/{id}/admit`
   - 提交入工作区判定，成功后创建 `pipeline run`
7. `POST /api/collaboration/sessions/{id}/halt`
   - 因循环或人工原因暂停

SSE 事件建议新增：

1. `collaboration_session_created`
2. `collaboration_assignment_updated`
3. `collaboration_queue_updated`
4. `collaboration_question_asked`
5. `collaboration_question_answered`
6. `collaboration_loop_warning`
7. `collaboration_admission_changed`
8. `collaboration_workspace_started`

## 15. UI/交互建议

### 15.1 对话区

1. 默认助理消息中可见“已进入协同准备 / 已派发 / 正在解除阻塞 / 已入工作区”。
2. 每条智能体消息需标识：
   - 发送者
   - 被 `@` 目标
   - 当前意图（分派/提问/回答/确认）
3. 显示当前回复队列。
4. 显示当前阻塞问题清单。
5. 循环风险出现时，顶部显示明显告警条。

### 15.2 工作区

1. 当协同会话进入 `workspace_execution` 后，自动跳转或同步到对应步骤页。
2. 工作区需显示该 run 来源于哪个 `collaboration session`。
3. 若工作区执行中再次遇到阻塞，可回流到对话区继续讨论。

## 16. 首期落地范围（M1）

首期建议只做最小闭环：

1. 仅限项目内对话
2. 仅支持 `默认助理 -> 编导 -> 大纲 -> 剧本`
3. 仅支持 `Outline` 自动入工作区
4. 仅支持单活服务实例
5. 循环检测先基于规则，不先做复杂模型判别

## 17. 风险与约束

1. 如果允许任意智能体自由互问，复杂度会迅速失控，因此必须强制依赖导向提问。
2. 如果没有显式队列，多个智能体同时回话会导致上下文污染。
3. 如果没有硬性循环阈值，协同会话会消耗大量 token 且无产出。
4. 如果“入工作区”门槛定义不清，系统会在信息不足时误启动正式流程。

## 18. 验收标准

### 18.1 功能验收

1. 用户给出创意后，默认助理可自动判断是否发起协同。
2. 编导可成功分派给大纲和剧本智能体。
3. 剧本可向大纲发问并得到顺序回复。
4. 当大纲无阻塞时，系统可自动进入 `Outline` 工作区。
5. 若仍缺关键信息，系统继续停留在对话区，不误入工作区。
6. 每 5 轮确实触发一次循环检测。
7. 达到循环阈值后，系统会暂停并提示用户裁决。

### 18.2 稳定性验收

1. 页面刷新后协同会话与队列可恢复。
2. 服务重启后未完成协同可恢复。
3. 不存在同一时刻多个智能体同时抢答导致的顺序错乱。
4. 所有入工作区和 halt 决策都有事件留痕。

## 19. 开发顺序建议

1. 先补 `collaboration session` 数据模型和 API
2. 再补编导分派器和回复队列
3. 再补上游追问与阻塞解除
4. 再补 5 轮循环检测
5. 最后接 `Outline` 自动入工作区

## 20. 结论

这个方案的关键不在“再加几个智能体”，而在于增加一层对话驱动的协同编排器。

系统需要明确区分三件事：

1. 用户对话
2. 智能体协同讨论
3. 工作区正式执行

只有这样，默认助理才能从“会聊天”升级成“会组织一组智能体把事做成”。
